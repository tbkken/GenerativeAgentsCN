## 4. 与系统能力的衔接

当前架构与地图 Schema 支持 `World → Sector → Arena → Game Object` 四层语义、地图碰撞配置、独立 Game Object 状态和状态外观。整张背景可作为 World 底层素材，空间语义可以单独覆盖，无须把每家商铺、每段路都切成图片。只有 Game Object 绑定被动 Skill。

设计阶段遵守以下边界：

1. 感知用 `world-perceive` 获取，受 Agent 视野与注意力限制。画面上存在摄像头，不代表 Agent 已看见设备、知道覆盖范围或知道自己被抓拍。
2. 出行计划、时间压力、风险权衡和记忆循环由 Brain/子 Skill 组织。17 个需求节点可作为职责说明，不转成系统强制流水线。
3. 位移用 `MOVE`，等待用 `WAIT`，普通活动用 `ACT`，对象状态修改通过合法 `SET_OBJECT_STATE` 和 World Commit。每 Agent 每 Step 最多提交一次世界动作。
4. 实际借道、路径和状态以已提交的 StepResult 和事实 payload 为准，不能以“我已进入机动车道”的模型文字证明。
5. 摄像头自动抓拍、处罚生效、交通拥堵计算、方向限行强制执行和遮挡判定，在本次素材准备中均未进行运行验收。基础移动、状态换图和感知能力不能直接证明这些交通专用规则已经实现。后续需逐项明确规则与实现入口。
6. 被动 Skill 只能提供观察反馈，不能自行处罚或修改世界。研究侧的客观记录与 Agent 实际收到的通知需要分开。
7. 护栏外观变化不等于碰撞或可通行性已变化；如果采用动态封闭缺口，必须另行核验它的实际通行规则。

以上是能力对接的设计边界，并非系统配置和运行验收结论。

## 5. 出图后的审视与后续待定项

首轮视觉检查已看到：上方机动车道和非机动车道箭头向左，下方向右；南侧护栏中段有一个开放缺口，其对面的中央绿化隔离带连续；两处正式过街通道贯穿主路；商铺背后的 U 形支路两端朝向南侧人行道和非机动车道；图内未画行驶人车或摄像头、处罚提示牌、信号灯。

需要在用户审视和后续网格配置时重点核对：支路与非机动车道之间的路缘及人行道能否实际通行；公交候车亭旁剩余骑行宽度是否足够；树冠、浅立面和门楼对 Agent 显示的遮挡。图片中看似连通不代表碰撞和导航已通过。通过画面审视后再确定逻辑网格、碰撞和空间语义。

初始角色应从住宅、驿站或入口附近开始正常出行，再逐步进入决策区。具体出生点、目的地、时间约束、视野和移动速度尚未配置。合法路线和借道路线的距离、耗时需要按最终地图计算，不提前编造节省分钟数。

源材料存在日期不同的地图工作表与区划说明，且部分角色位置栏仍保留旧描述。例如 Agent 表 `Q3` 是“客村出租屋”，`D3:E3` 是“青年合租普通住宅 / S10-06”；后续角色录入要明确使用哪一版，不能混用旧坐标。源表已指出的地铁接驳角色和育婴家庭等待补事项也保留待定，不在首张地图阶段擅自补写人设。
