# 交通治理实验：系统能力评估与摄像头执行设计

状态：历史评估稿，保留最初评估时的源码结论与未采用方案。2026-09-13 用户随后确认“Game Object 绑定 Skill 即具备自主执行、感知与交互响应，优先用大模型驱动”，并授权实现。下文的被动执行现状、缺口状态和确定性场景脚本建议已被后续决定替代，不能作为当前配置依据。

当前实现见 [Game Object Skill 运行合同](../../game-object-skill-runtime.md)，工程验证见 [实现验证记录](../../game-object-skill-verification-2026-09-13.md)。已接入对象独立身份、模型执行、有限感知与真实路径证据、自身状态提交、请求者隔离回复、活动幂等键及文件恢复回放。具体摄像头判定、连续活动分段和交通规则由实验 Skill 定义，尚未用真实模型验收；秒级交通动力学也不在本次实现范围内。本实验仍未录入系统、封存或启动正式 Run。

关联资料：[需求](需求.txt)、[首轮实验方案](首轮实验方案-v1.md)、[实验目标与地图](实验目标与地图设计-v3.md)。

## 1. 结论与本轮范围

现有系统具备空间感知、Agent 自主决策、实际路径执行、对象状态、事件记录和文件回放的基础。它可以支撑路线选择的准备工作，但目前不能仅靠摄像头图片与一个被动 Skill，完成“实际违规 → 自动抓拍 → 处罚 → 定向通知”的客观执行链。

摄像头应作为 Game Object 出现在地图上。Agent 对它的感知、查询或合法操作可以使用公共 MCP；**自动抓拍应由世界执行真实动作时触发，不能依赖被拍摄者主动调用工具。** MCP 是能力接口，是否自动执行、由谁执行、依据哪些事实执行，仍需运行机制保证。

本轮方案研究一次出行的即时选择，已约定不投递本次出行的新处罚通知。因此优先补齐客观违规判定与抓拍记录，处罚执行、延迟通知和后续出行学习可后置。不能因为暂不需要通知，就把“满足抓拍条件”写成“已经发生抓拍”。

## 2. 现有红绿灯究竟实现了什么

仓库有 `traffic-signal-state` 与 `crosswalk-signal-advisor` 两个相关示例，均是主动交互触发的 Game Object 被动 Skill，没有专门的红绿灯 MCP。

当前调用链为：

1. Agent 通过 `world-perceive` 获取附近对象与可用交互。
2. Agent 提交 `world-act(action_type=INTERACT, selection_key=...)`。
3. 被动脚本读取对象状态和当前 Step，计算灯色，返回自然语言提示。
4. 交互提交后，提示进入该 Agent 下一轮的外部观察；Brain 决定等待或移动。

`traffic-signal-state` 支持红、绿两相；`crosswalk-signal-advisor` 还支持闪烁清空期及剩余步数。显式灯色可以覆盖周期计算。两个脚本都没有让车辆自动停车，也没有把计算出的相位主动提交为对象状态变化。

因此可以复用它们的“实例参数 + 确定性状态计算 + 观察反馈”思路，但不能据此认定平台已有自主运行的交通设施。

还有一个时间边界：`INTERACT` 占用本轮唯一世界动作，返回观察在下一轮使用；下一轮灯色可能已改变。交通实验需要明确观察时刻与实际通过时刻，不能把上一轮的绿灯提示直接视为本轮通行事实。若要求当轮看到实时灯色，应另行设计公共感知中的当前相位投影，不在同一步追加第二次世界动作。

## 3. 能力盘点

“已有”表示存在可定位的实现，并不等同于本实验已通过运行验收。

| 实验需要 | 当前实现及限制 | 判定 |
| --- | --- | --- |
| 四层空间、附近设施与提示信息 | `world-perceive` 按语义节点查询，并限制视野和注意力；地图图片仍需配语义与碰撞 | 基础已有 |
| 合法路线与违规路线的真实选择 | 支持寻路、MOVE 和真实路径记录；寻路依据碰撞，未发现道路法规约束 | 可配置空间，须核验具体路线 |
| 摄像头外观与状态查询 | 可用 Game Object、可见状态及被动反馈表达 | 基础已有 |
| 骑手没看见摄像头，也没有主动查询时被抓拍 | 当前被动绑定仅在 Agent 选择交互后执行；主循环未发现摄像头轨迹触发入口 | 缺少执行能力 |
| 客观判定实际违规 | 每步已有 `executed_path`、起终点与地址；未发现交通规则判定器 | 有事实基础，判定待实现 |
| 实际抓拍与处罚事实 | 有通用事件、StepResult 与文件提交设施；未发现本场景的抓拍、处罚记录链 | 记录基础可复用，业务链缺失 |
| 只让当事人收到通知 | 已有按 Agent 隔离、投递后清空的被动观察队列，且队列纳入检查点 | 通道可参考；处罚通知的来源、时机和去重尚无实现 |
| 连续违规去重、暂停恢复不重复抓拍 | 有运行检查点与稳定事实 ID 基础；没有摄像头的违规事件段和抓拍账本 | 需专门接入并验收 |
| 隐藏覆盖范围、抓拍概率和内部记录 | 当前对象 `state` 会进入感知结果，未见公开字段与内部字段的分离投影 | 不能直接把秘密规则装进对象状态 |
| 限制谁能关闭摄像头、修改灯色 | 当前 `SET_OBJECT_STATE` 校验附近可用性及非空状态补丁，未见对象操作角色或字段权限校验 | 设施控制权限需补齐 |
| 机动车流、排队、容量与拥堵延误 | 当前寻路使用碰撞网格，移动预算按步长计算；所查执行链未发现车辆占位、跟驰或信号通行控制 | 不能宣称已有交通动力学 |
| 秒级灯色周期与过街时刻 | 当前 `stride_minutes` 是至少 1 的整数，每步可经过多格；没有逐路径点的秒级通行时间 | 分钟级抽象可用，精细交通需另行设计 |

这些是针对尚未构建的摄像头场景的适配缺口，不是已经复现的页面故障。没有 Experiment、Run、Attempt 或 Step 验收证据，不能登记为已修复或已验证。

路线选择还需避免一个混淆：Agent 只提交远端目的地时，当前寻路会选择可达的短路径；如果短路径穿过机动车道，不能据此直接断言 Agent 明确选择了违规捷径。首轮需通过核验过的路线途经点表达不同选择，分别检查决策证据和每段实际路径。把机动车道全部设成碰撞区又会消灭违规选项，因此不能用碰撞代替道路规则。若要直接按合法区域约束寻路，需要另行设计通用的路径约束能力。

## 4. 建议的职责划分

### 地图对象：摄像头、提示牌、信号灯

保存设施的空间身份、位置、外观及应当被观察到的信息。摄像头的设备位置、骑手能感知它的范围、真实抓拍覆盖区是三件不同的事，不能简单用同一个交互半径代替。

隐藏的检测参数和执法记录不放进目前直接对 Agent 返回的 `state`。看到一台摄像头，也不等于知道其精确覆盖范围、是否成功识别自己或真实抓拍概率。

### Brain 与子 Skill：主观理解和行动选择

Brain 结合实际感知、任务、截止时间和自身记忆，决定走哪条路线、是否等待。它可以不相信提示、没有注意到摄像头，或选择违规路线。它不能自行宣布违规认定、抓拍成功或处罚发生。

### 场景规则：客观判断

建议由实验包内的确定性规则脚本定义违规区域、合法例外、设备工作条件、覆盖判定与去重规则。规则只读取运行时提供的事实并返回待校验结果，不直接改世界、写数据库、调用外部服务或修改 Agent 记忆。

这类规则不是现有“只返回观察文本”的被动 Skill；当前仓库尚无对应的通用触发合同。文件可按约定组织在 `skill/`，但在系统扩展完成前，不能把文件放进去就宣称能够执行。

### Runtime：触发、校验、提交和恢复

建议在已校验的世界动作产生实际执行结果后、当前 StepResult 冻结之前，运行声明的场景规则，将获准的后果与原动作一起进入事实提交边界。

```text
Brain 选择行动
    ↓
world-act：本轮唯一世界动作
    ↓
Runtime 校验并确定本步实际执行路径
    ↓
包内规则读取实际路径、设备状态和空间规则【拟新增】
    ↓
Runtime 校验违规／抓拍结果并形成事实【拟新增】
    ↓
StepResult → 文件、检查点、回放
    ↓
若实验明确启用反馈，按政策向当事人投递【后续】
```

这项设计保留 `world-act` 为 Agent 唯一世界动作入口。摄像头结果作为真实动作的客观后果进入同一提交链，不让骑手再调用一次“抓拍自己”，也不让规则脚本直接修改回放。

若以后需要“无人动作时灯色变化”“摄像头定时启停”“延迟通知到期”等能力，还需显式定义虚拟时间触发的合法系统后果及其提交合同。不能借本次移动后果设计，默许一条任意改世界的后台入口。

**这是待讨论的通用能力扩展，不是现有能力。** 实施前需确认它与仓库 `AGENTS.md` 第 5、8 节的世界动作与事实边界如何衔接。不能把被动 Skill 改成主动修改世界，也不能把交通业务流程硬编码进内核。

## 5. 摄像头最小执行合同草案

### 输入

- 运行与事实身份：`run_id`、`attempt_id`、Step、原动作事实身份、当前 Agent 稳定身份。
- 权威运动事实：起点、本步 `executed_path`、终点；原地停留时使用实际位置，未消费的计划路径不算经过。
- 世界条件：包内道路区域与合法例外、设备工作状态、真实检测覆盖区、本轮虚拟时间。
- 历史状态：该 Agent 是否仍处于同一次连续违规中、该设备是否已对该违规记录抓拍。

不把 Agent 的“我没有违规”、是否调用摄像头交互、是否注意到摄像头或模型输出的处罚描述作为客观判定依据。

### 判定顺序

1. 按实际经过的道路区域判断是否违规，排除已明确定义的合法穿越；物理上可走和规则上允许通行分别判断。
2. 判断违规发生的那段实际路径是否落在工作的摄像头覆盖区；不能把“某处违规”和“另一处经过摄像头”简单相与。
3. 按预先固定的设备规则判断是否形成抓拍，并绑定原始路径证据。
4. 首轮建议以“同一摄像头 + 同一 Agent + 同一次连续违规”为去重单位。持续停留或跨多步行驶不重复抓拍；退出后再进入是否算新违规须写入实验规则。
5. 如将来启用处罚，另按处罚规则产生事实；抓拍记录本身不等于处罚，通知也不等于处罚本体。

首轮建议固定设备开启和确定性识别，暂不引入随机漏拍。若后续研究漏拍概率，随机来源必须归属于运行并可恢复，不能每次重试重新抽样。以上均为待定参数建议。

### 输出与保存

违规、实际抓拍、处罚、通知分别形成有证据的记录。每条已提交的世界事实含 SPO 与足够回放的 `structured_payload`，记录原动作、设备、相关路径段、判定依据及虚拟时间。

规则执行失败应产生诊断或按明确策略阻止该步提交，不能静默记成“没有违规”或“没有被拍”。规则身份及内容哈希随实验包封存；不是公共作者资源的业务 Revision。

违规事件段、已抓拍账本和待通知状态必须进入 Run 的持久化与恢复合同。恢复后继续同一事件段，不因新建 Attempt 重复记罚。普通帧 ID 或“每步只运行一次”不能替代跨步去重。

### 可见性与操作权限

研究记录与 Agent 观察分开：内部抓拍事实不默认成为附近所有人的可感知 Event。只有实验规定的闪光、提示声或定向通知才能使 Agent 获知相应信息。

设施控制操作要明确主体与字段权限。骑手能看到设备，不代表可以修改摄像头的工作状态、抓拍账本或红绿灯周期。现有的附近对象检查不足以表达这种约束。

## 6. 最小验收例子

以下为未来能力实现的验收要求，本次未运行。

| 情形 | 应有结果 |
| --- | --- |
| 实际违规经过开启设备的覆盖区，未查询、未看到摄像头 | 按固定规则产生抓拍；不能因缺少 INTERACT 而漏记 |
| Agent 看到了摄像头，但沿合法车道行驶 | 不产生违规抓拍 |
| 本步起终点都在覆盖区外，中间违规路径经过覆盖区 | 根据中间路径判断，不能只看终点 |
| 计划会进入覆盖区，本步移动预算尚未到达 | 不提前抓拍 |
| 经过覆盖区内的合法通行例外区域 | 不误报违规 |
| 摄像头关闭，或违规发生在其覆盖区外 | 可有违规事实，无该摄像头抓拍事实 |
| 同一次连续违规跨数步或中途 WAIT | 按事件段去重，不能每步重复抓拍 |
| 暂停恢复或失败重试 | 不重复事实和通知；保持原事件段与判定依据 |
| 普通骑手尝试关闭摄像头或改规则 | 权限拒绝；保留诊断，无越权状态变化 |
| 首轮 C1/C2 出现抓拍 | 研究侧可记录；不自动向当事人发送本次处罚反馈 |
| 读取回放与研究报告 | 实际违规、满足抓拍条件、实际抓拍、处罚分别可核验；未知不计零 |

灯色方面还需单独验证：同一虚拟时刻是否一致、跨步查询是否过期、回放状态是否与判定相符。若没有步内时间模型，不把一次多格 MOVE 解读成已知秒级过灯时刻。

## 7. 对实验构建顺序的调整

优先审视本稿中的环境触发与事实提交边界，再决定首轮采用哪种能力范围。

- **完整自动抓拍方案：** 先明确并实现通用触发、内部规则与公开观察隔离、控制权限、抓拍事实和恢复去重。随后再确定摄像头位置及覆盖范围，制作设施素材和配置 Brain。
- **仅使用现有能力的范围：** 可构建设施可见性与路线选择演示，并根据 Run 轨迹事后计算违规和“满足抓拍条件”。必须明确这属于研究侧派生分析，不能作为系统已经自动抓拍或处罚的证明；也不能无说明沿用原方案对工作设备的承诺。

推荐首轮目标仍保留真实抓拍记录，暂不扩展到罚款金额、即时处罚通知、车辆跟驰和复杂交通信号控制。当前分钟级时间粒度则必须在路线成本定稿前明确接受为实验抽象，或另行提出时间能力扩展。

不改变已审视的地图构图，不继续系统配置，也不把能力缺口通过提示词包装成既成事实。
