# 系统原理与使用：能力盘点及递进案例方案（审校修订稿）

核对日期：2026-09-09。本文是教材与案例的设计稿，不表示案例已经实现或通过验收。依据当前工作区源码、仓库架构约束、样例文件和管理台操作记录；具体运行进度与问题记录保存在各案例的验证目录。


## 目录使用说明

本文件是书稿总纲，不是功能承诺清单。案例分为三类：

- **主教程案例**：从干净工作区按章节步骤应能完成，作为读者照做的主线。
- **失败/对照案例**：有意制造不可达、信息过期、权限或隔离边界，用来学习诊断方法。
- **出版验收案例**：用于确认当前版本是否达到可写入主教程的稳定程度；未通过时只进入“开发中/实验性能力”说明。

每章除操作步骤外，必须明确读者学会的能力、可观察结果和证据位置。系统事实以 MCP、World Commit、StepResult 和 Run 文件为准；页面截图用于说明操作，不替代事实证据。

## 审视结论与本次调整

原方案的主线是成立的：先用一个 Agent 完成连续生活闭环，再逐步深入移动边界、记忆证据、物品反馈、对话、子 Skill、共享状态和多人协作。案例 1 只使用最小进度便签和一次可见的桌面状态变化来支撑生活连续性，不提前展开复杂记忆机制。本次审校保留以下四项收敛：

1. 将“运行监督与恢复”拆成案例 7 之后的微案例，避免在多人综合案例中第一次讲暂停、检查点和 Attempt 身份。
2. 将文件协议与离线回放保留为附录，案例 8 只负责综合行为与质量观察，避免把业务机制、运维机制和包格式塞进一个案例。
3. 在能力地图中补齐 Crowd 展开、双模型预设、逻辑调用与物理尝试、包完整性等容易被忽略的边界；明确 Crowd 是作者选择集，Runtime 运行的是导入后的独立 Agent。
4. 把自定义 Evaluator 标为“已复制、未由当前 portable Runtime 执行”，并增加专门的出版验收，避免把确定性诊断、Brain 合规评估和业务评估混为一谈。

因此，书中“主教程”只承诺已经通过端到端验收的能力；源码存在、资源可以保存或文件可以读取，都不能单独作为可用性证明。

## 读者学习成果

读者完成全书后，应能够：

1. 从零创建四层地图、角色、Brain Skill 和自包含实验包，并解释每项配置的作用。
2. 判断角色在当前 Step 真正知道哪些空间、对象、事件和记忆。
3. 使用 `world-perceive`、记忆 MCP 与 `world-act` 完成可验证、可回放的行动。
4. 区分 `ACT`、`MOVE`、`WAIT`、`SPEAK`、`INTERACT` 和 `SET_OBJECT_STATE` 的语义边界。
5. 设计子 Skill、被动 Skill 和多人对话，并验证身份隔离、一次性反馈和会话复用。
6. 读取 StepResult、Trace、Checkpoint 和质量结果，定位失败原因而不是凭模型文本猜测。
7. 校验、导出、续跑、重跑和离线回放 `.gaexp`/`.garun`，理解 Studio、Runtime、Replay 的文件协议边界。

能力覆盖速查：`ACT` 和基础 `MOVE` 在案例 1，导航与感知边界在案例 2 深入，`WAIT` 在案例 5 和运行控制微案例，`INTERACT` 在案例 4，`SPEAK` 在案例 5；`SET_OBJECT_STATE` 在案例 1 用于单次桌面变化，案例 7 再讲共享状态与反馈传播。记忆 `append/search` 在案例 1 仅用于本人进度便签，案例 3 专讲记录 ID、有效条目、访问证据及上下文对照，`supersede/invalidate` 在案例 7；空间语义在案例 1/2，视野半径和带宽在案例 2 对照；Brain 和子 Skill 在案例 1/6；监督和检查点在微案例；Evaluator 只在案例 8 做可选配置并按当前状态报告；`.gaexp`/`.garun` 在附录 A。这样可以在出版前逐项检查“能力已讲解”与“能力已通过验收”是否被混淆。

## 预备章：工作区、模型与最小实验

预备章只讲环境准备，不引入新的仿真机制：创建或选择作者资源、配置聊天模型预设和 embedding 模型预设、注入目标环境变量、检查模型连通性、理解凭据不进入包，以及认识 DRAFT → SEALED 的边界。正式第 1 章再创建第一张教学地图。这样读者不会把“模型服务可用”误认为“实验已经成功”，也不会把本地启动脚本当成系统能力。

## 一、书的主线

让读者逐步回答：一个角色怎样在一个有规则的世界里，通过观察、记忆和自然语言行为说明，采取可验证的行动？

采用“先完成一次最小实验，再解释其原理，再增加一个新能力”的顺序。不按管理台菜单顺序写书，也不在第一章要求理解四个模块、完整文件协议或复杂大脑模式。

全书按能力递进组织多个小型教学场景。案例 1 使用一套有卧室、书房、厨房和餐区的住宅，后续案例各自提供独立地图和素材，不能依赖前一案例的文件或公共运行副作用。最后再进入溪谷大学综合案例。

## 三、讲解顺序与案例

### 案例 1：陈明远醒来后的晨间工作启动

- 规模：1 人、1 个 World、1 个 Sector、5 个 Arena、4 个 Game Object（床边、工作书桌、料理台、早餐餐桌）；家中通道只有 Arena 语义。地图使用一张完整住宅背景和桌面两态切片；当前验证配置为 32 步、每步 3 分钟，从 2026-09-09 07:00 Asia/Shanghai 开始。
- 读者问题：一个角色怎样在有空间约束的家中完成一段连续、可信的晨间生活？文字计划怎样在不同地点之间变成可回放的动作？
- 页面操作：导入住宅背景，在其上配置四层语义与碰撞，给工作书桌绑定整理前后切片；上传角色头像和行走图，按本地图选择 3 格显示大小；选择模型和 Brain，创建实验并确认初始位置，检查、封存、运行、回放。具体操作集中在 [案例 1 浏览器清单](sample/01-morning-routine/settings/browser-authoring-checklist.md)。
- Brain 要点：每轮感知真实位置与状态，并检索自己的最新晨间进度便签；跨房间先查询最终可走站位，再以同一最终坐标提交 `MOVE`，不能把 `next_coord` 当整段行程；生活活动使用 `ACT`。动作前追加“已确认事项 + 待确认动作”的累计便签，下一轮对照真实结果确认；整理资料后用独立一轮 `SET_OBJECT_STATE` 将书桌的顶层 `state` 设为 `tidy`。约二十项活动依照真实进展展开，不按 Step 编号排程。
- 引入：四层空间、Brain、感知、导航、世界动作、最小 `memory-stream-search/append` 进度便签、`ACT`、`MOVE`、单次 `SET_OBJECT_STATE`、虚拟时间、移动预算和 StepResult。
- 验收：按 32 步的观察配置检查时间与行为；每步至多一次成功的 `world-act`，移动使用已校验路径且不穿越碰撞格；每步保存按 `Asia/Shanghai` 带偏移的虚拟时间并按 3 分钟递进；ACT、MOVE 和对象状态事实具有 Event(SPO) 与非空 `structured_payload`；回放显示正确的地址变化与整理后的桌面，进度便签不把待办提前写成完成。早餐吃完、资料整理完和开始工作是事实或可选评估指标，不是 Runtime 的硬性完成条件。当前已完成一次 32 步晨间行为验证，跨 Attempt 的 5 项质量记录和浏览器结果 ZIP 已复验归档；普通结果 ZIP 不等于正式 `.gaexp` / `.garun`，出版图片与正式包协议复现仍需专项验收。具体结果见 [案例验证记录](sample/01-morning-routine/settings/verification-record.md)。
- 不展开：复杂检索策略、记忆替代与失效、社交、反思、被动 Skill 和子 Skill。便签只保存本人的生活进度，不能代替世界事实或驱动画面。

### 案例 2：穿过门口，到阅读角看书

- 规模：1 人、两个相邻场所，一扇明确门洞、一段短路；建议 6–8 步，每步 1 分钟。
- 读者问题：画了地板就能走吗？知道目的地就等于已经到了吗？
- 页面操作：使用本案例独立的完整背景与人物素材，新建双房间地图并定义墙体、可走位置、入口，完成两点路径检查；先通过感知获得阅读角的完整语义地址，或把地址明确写入该角色记忆后再导航。选择本案例 Map、Crowd 和 Brain 新建独立实验，再确认包内位置与资源；不依赖上一案例的资源或运行副作用。
- Brain 要点：查询阅读角的完整地址，朝最终目的地移动；只有实际到达后才阅读。不要只把 next_coord 当成整次行程的目标。
- 验收：未穿墙；已查询路线不产生位移；已提交 MOVE 路径与回放一致；ACT 阅读发生在阅读角。
- 对照：分别测试“门被挡住”“只有地点名称但没有完整地址”和“请求超过 vision_radius/attention_bandwidth”的实验，观察不可达、知识不足和候选裁剪；不让模型假装到达或借请求扩大系统视野。
- 教材价值：在这里解决步长、移动预算、路径长度的量纲问题，不拖到两日校园案例才发现迟到。

### 案例 3：记住一件事，过一会儿再想起来

- 规模：1 人、一间独立的小型室内空间，两个普通物品；建议 6–8 步。
- 读者问题：模型这一轮说过的话，下一轮究竟从哪里获得？
- Brain 要点：将亲眼观察到的具体事实写入本人记忆；稍后检索并用于选择活动。使用自然语言内容，保留对象名称帮助当前词项检索。
- 验收：存在真实 append 返回的记忆 ID，后续 search 返回同一有效条目，出现访问记录；不能仅凭模型复述一句话认定记忆正常。
- 局限：检查后续上下文是否仍包含同一事实；能检索出记录不等于证明行为完全依赖记忆。书中分别讲“存储链路成立”和“行为因果证据”。
- 深入：在案例 1 最小进度便签的基础上，专门检查记忆写入、读取、有效记录 ID 与访问历史，区分存储链路和行为使用证据；替代、失效放到案例 7，避免一次讲太多。

### 案例 4：向公告栏查询活动安排

- 规模：1 人、1 个有真实初始内容的公告栏；建议 5–8 步。
- 读者问题：物品怎样回应角色？为什么图片中的字不自动等于系统事实？
- 页面操作：给公告栏配置可交互信息、初始状态及被动 Skill，并验证依赖已随实验导入。
- 被动 Skill 要点：根据真实对象状态返回活动地点和时间；没有的信息明确不知道，不编造。
- Brain 要点：发现公告栏、INTERACT、下一轮处理反馈，随后记忆或行动。最后一步不安排需要下一轮消费的首次交互。
- 验收：交互动作有事实；反馈下一轮到达发起者且只投递一次；反馈内容与对象状态一致；被动 Skill 未直接改变世界。
- 状态：待先完成管理台闭环验证后纳入可照做章节。

### 案例 5：两个人在阅读角见面

- 规模：2 人，初始距离很近；建议 8–12 步。
- 读者问题：别人能看见我的记忆吗？一句回复怎样属于同一段对话？
- 页面操作：组成两人人群，各自配置背景和私人信息，显式配置附近位置。
- Brain 要点：先观察是否有对方；一人先到时用带原因和截止 Step/虚拟时间的 WAIT 等待；使用真实会话 ID 回复；把有意义的交流记下来。不预写双方台词。
- 验收：附近人物感知正确；双方各有实际 SPEAK 提交；回复复用同一 conversation_id；每次 SPEAK/WAIT 都按 StepResult 的 Event、SPO 和非空 `structured_payload` 验收，模型原文只作 Trace；未说出口的私人信息不从他人的 memory search 返回。
- 边界：自然语言保密要求只是行为约束；跨身份访问拒绝的强隔离验证应放在附录，不用一次没泄漏就宣称安全已证明。等待必须在结构化动作载荷中带 `expected_until_step` 或 `expected_until_time`，才能被 Supervisor 识别为有边界计划，不能把正常等待误报为卡死。

### 案例 6：商量一件事，再整理共同决定

- 规模：2 人，另建独立的双人空间实验；建议 10–16 步。
- 读者问题：什么时候需要子 Skill？反思是系统自动做的吗？
- Brain 要点：遇到分歧时调用“交流建议”子 Skill；有足够新经历时调用“整理经历”子 Skill；在动作前保存重要结论，最后由 Brain 提交动作。
- 引入：Brain 自主选择调用条件、自然语言子调用、计划与反思作为可选模式。
- 对照盒子：先对“交流建议”做独立文本试运行，再在真实实验中调用；比较两条路径的上下文、身份注入和 Trace。管理台入口未接通前，这个盒子只作为开发/实验性内容。
- 验收：Trace 中可定位子 Skill 调用与返回；返回被 Brain 使用；没有强制每步交谈或反思；重要结论写成记忆。不会把中间文本直接当作世界变化。
- 对照：两个独立实验只改变是否允许该整理 Skill。比较调用数量、时间、信息一致性；不预设加入反思一定更好。

### 案例 7：公告更新后，修正旧计划

- 规模：2 人，一个负责发布通知、一个读取通知；建议 12–16 步。
- 读者问题：共同世界改变后，私人记忆怎样更新？旧事实该删除吗？
- 过程：读取者先获知旧地点；发布者通过 SET_OBJECT_STATE 修改公告地点；读取者之后重新交互，从真实反馈得知变化，用 supersede 替代旧记忆，再调整行动。
- WAIT 用于有明确截止的等待，变化由角色的合法动作引起，不新增系统硬编码排程或定时事件器。
- 验收：每次 `SET_OBJECT_STATE` 都有 Event(SPO) 和非空 `structured_payload`；更新前后对象状态可回放；被动响应与实际状态一致；旧记忆仍留历史但不是 ACTIVE；默认检索返回新事实；角色在获知消息前不得表现为已经知道变更。
- 可选练习：对“已作废且没有替代内容”的通知使用 invalidate。
- 边界：先验收对象编辑及状态动作链路。不把发布者职业当作权限实现，不加入未经验证的并发抢占、借还锁或管理员权限。

### 微案例：暂停一次，再从检查点继续

- **规模**：复用案例 3 的一人、6 步实验，在中间 Step 发出暂停请求，再继续或取消；随后从一个完整检查点续跑。
- **读者问题**：暂停、取消、恢复和重跑分别改变什么？怎样证明恢复没有重复动作、记忆或会话？
- **过程**：观察 `QUEUED → RUNNING → PAUSED → RUNNING → FINALIZING → COMPLETED` 的边界；检查 `status.json`、最后完整检查点和 Attempt 日志；续跑保持 `run_id`，创建新的 `attempt_id`，从下一 Step 继续。
- **验收**：暂停和取消在 Step 边界生效；检查点、帧、记忆、对象变化保持幂等；恢复不产生零进展 Attempt；逻辑调用与物理尝试分开统计；质量报告在 `FINALIZING` 阶段完成后才结束。
- **失败练习**：注入一次可恢复格式错误或瞬时失败，验证重试有错误分类、预算和可中断等待；不要用无限重试掩盖问题。

### 案例 8：四人协作进行一次校园活动

- 规模：4 人、2–3 个相邻场所；先设计约 12–24 步的短时活动，按案例 2 的移动结果校准。
- 场景：教师准备一次讨论，两名学生带着不同问题参加，工作人员发布一次场地变更。所有信息传播必须经感知或交流发生。
- 集成：人物差异、时间安排、移动、私有记忆、对话、可选子 Skill、对象状态和反馈；可选配置一个显式业务 Evaluator，但必须把它的结果与 Run 是否完成分开呈现。
- 观察指标：到达情况、信息传播路径、过时记忆是否修正、是否出现重复会话、每人调用成本。未到达也是应解释的实验结果，不强制改成成功。
- 不引入：动态红绿灯、全天作息、复杂维修权限和大量地点；职业或角色描述不构成权限。先保证每个机制已有独立证据。
- 毕业扩展：溪谷大学四人两日生活，放在完整短案例通过之后，专门研究长期行为、时间成本与偏离。长 Run 的现场观察只能作为开发日志，不能写成已通过案例。

## 四、穿插讲解的原理，不另堆复杂生活案例

| 放置位置 | 主题 | 演示与证据 |
| --- | --- | --- |
| 案例 1 后 | 世界事实与回放 | 一条 ACT 从 MCP 到 StepResult、SPO、payload，再到画面；回放不重新调用模型 |
| 案例 2 后 | 时空与可达性 | 地图格、虚拟分钟、实际耗时分别是什么；路线查询与实际消费路径分别检查 |
| 案例 3 后 | 记忆与上下文 | 私有持久记录、当前上下文、LLM 参数知识不是一回事；当前检索实现的实际限制 |
| 案例 5 后 | 身份、会话与动作约束 | 系统注入角色身份，一步一次世界提交；拒绝和回退应可诊断 |
| 案例 6 后 | 能力组合原理 | Brain、子 Skill 与公共 MCP 的职责；展示少量真实调用而不是大段术语 |
| 案例 7 后 | 世界事实与个人认识 | 对象已经改变不代表所有角色已获知；区分观察、记忆和共享状态 |
| 案例 8 前 | 运行监督 | 用已掌握的小实验演示暂停、取消、检查点与续跑，不通过把案例拉长来制造困难 |
| 案例 8 后 | 文件协议及四模块 | Studio → gaexp → Runtime → Run/garun → Replay；公共资源删除不应破坏独立实验 |

暂停、继续、取消和恢复分别验收。新跑创建新 Run；续跑保持 Run 身份并创建新 Attempt。恢复要检查动作、记忆、会话及对象更新是否重复。已有恢复问题不能靠“直接重跑一次”作为恢复通过的证据。

可移植演示需单独验证导出、完整性校验、目标环境密钥注入、无 Studio 执行、离线回放与改名后的身份保持。固定随机种子并不保证 LLM 每次输出相同；区分“事实回放确定性”与“重新推理结果可能不同”。

## 五、每章统一的案例交付格式

1. 本章只回答的核心问题，以及读者能观察的结果。
2. 前置条件：明确地图、角色、模型、所需能力，不隐式使用系统默认地图。
3. 资源清单与完整自然语言 Skill；关键参数说明为什么这样设。
4. 可逐项照做的管理台步骤和实际截图；不能用接口操作冒充页面可用。
5. 一个独立实验包及其包内身份/哈希；适用的代码提交、模型和环境记录。模型密钥不入书、不入包。
6. 一个真实参考 Run、关键步骤证据与预期变化范围；不要求读者复现逐字台词。
7. 验收表：用户功能、系统合同、行为质量分别判断。
8. 一项失败或对照练习，解释如何定位问题；与正常教程清楚分开。

步数仅为设计建议，应先用本地 Qwen 实测，再给出耗时范围。不承诺所有案例几分钟内完成。粗略成本按“人数 × 步数 × 每步真实调用数 × 单次耗时”估算，并单列重试；物理尝试与逻辑调用不能混计。

## 六、落地与出版准入

先只做案例 1、2、3，全部通过管理台从零搭建并完成短 Run。三例分别解决“连续生活闭环”“移动与感知边界”“记忆存储及使用证据”，它们是后续所有案例的基础。

接着验证案例 4、5，重点是物品反馈一次性投递、会话隔离和有界 WAIT；再做案例 6、7，随后完成运行控制微案例，最后组装案例 8。附录 A/B 单独做包协议、评估器和身份边界验收。整套案例可以兼做产品回归集，但回归要求不是用户正式实验必须经过的强制试跑。

每例必须同时满足：

- 从干净作者工作区按说明可建立资源，不依赖隐藏种子或旧数据库残留。
- 通过管理台完成必需配置和启动；缺按钮或必须绕接口就登记阻塞。
- Run 正常结束，真实事实足以证明本例目标；质量问题单独记录。
- 导出及重新打开按该章范围可用；参考截图和实际版本一致。
- 不需要清缓存、手改数据库或临时改系统配置才能完成常规操作。

未通过部分可以作为“开发中 / 实验性能力”讨论，但不放在读者照做就应成功的主教程中。

## 附录 A：从实验包到离线回放

- **规模**：单独准备一个与案例 1、2 同样精简但文件独立的实验，另准备一台不启动 Studio 的 Runtime/Replay 环境。
- **读者问题**：为什么实验和运行不依赖数据库？改名或移动文件后，身份是否仍然可靠？
- **过程**：校验并封存 `.gaexp`；注入目标环境密钥后创建 Run；暂停或完成后封存 `.garun`；安全解压到新目录并续跑；最后在无 Studio 环境离线回放。
- **验收**：包内 `experiment_id/run_id/attempt_id` 保持合同；完整性校验通过；续跑保持 `run_id` 且创建新 `attempt_id`；Replay 不调用模型、不读取数据库；改名后仍按包内身份工作。
- **定位重点**：区分事实回放确定性和重新推理可能不同；记录密钥注入、校验失败和检查点边界。

本附录案例不增加新的业务机制，专门把本系统最具辨识度的可移植、可恢复和可审计能力变成读者亲手完成的操作。

## 附录 B：质量评估与身份边界

- **评估器验收**：创建一个 Evaluator，检查包内 `evaluation/evaluators.json` 是否存在；运行后再检查 `artifacts/quality-report.json`，明确区分确定性质量诊断、Brain 合规评估和业务 Evaluator。当前 portable `ga_runtime` 执行链只生成确定性诊断，报告中的 `NOT_EVALUATED`/`SKIPPED` 不能解释为业务通过。
- **身份边界验收**：用失败/对照实验尝试伪造 Agent 身份、读取另一 Agent 的记忆、重复提交第二次 `world-act`，并检查拒绝原因是否进入 Trace 或质量结果。自然语言“请保密”只能作为行为约束，不能替代内核隔离证明。
- **资源副本验收**：导入 Crowd、Agent、模型预设、Skill 和 Evaluator 后，删除或归档公共资源，再从实验包运行并回放；若仍依赖 Studio 数据库，应判为包协议失败。

这些内容在当前执行链尚未全部通过出版验收前，放在附录和开发中说明，不作为主教程的稳定承诺。

## 七、本次核对入口

- `AGENTS.md`：职责边界、动作原语、身份隔离、文件化运行和禁止引入的设计。
- `docs/capability-composition-platform-design.md`：四模块与包协议架构。
- `src/generative_agents/ga_runtime/capabilities/server.py`：公共 MCP、导航目标知识边界、动作校验。
- `src/generative_agents/ga_runtime/skills/brain.py`：人物上下文、运行与质量评估入口。
- `src/generative_agents/ga_runtime/memory/stream.py`：文件记忆、词项检索、替代/失效和记忆事件。
- `src/generative_agents/ga_studio/resources/trials.py`、`ga_runtime/skills/trial.py`：独立文本试运行的准备和执行边界。
- `src/generative_agents/ga_studio/experiments/workspace.py`：资源物理导入与实验内容。
- `src/generative_agents/ga_runtime/lifecycle/executor.py`：执行阶段、最终质量报告和运行文件。
- `src/generative_agents/ga_replay/reader.py`、`adapters/web/routes/results.py`：文件读取、回放及管理台结果接口。

现场 Run 的进度、迟到情况和临时 PermissionError 不写入书稿主线；它们只进入带版本、包哈希和证据路径的开发日志。出版验收必须引用冻结的参考 Run、StepResult、检查点和质量报告，不能引用正在变化的 Run 观察。
