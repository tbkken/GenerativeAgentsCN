# 案例 1 独立地图：陈明远的家

## 文件

- `map-definition.json`：地图作者定义的历史导出记录。当前浏览器地图为 32×24、32px Tile；四层节点、碰撞和切片绑定应以浏览器最终导出为准，不能直接把此 JSON 当作当前事实。
- `semantic-addresses.json`：旧地图的地址索引，不能作为当前坐标来源。
- `collision-and-placements.json`：旧地图的碰撞与站位记录，不能作为当前可导入资产；使用下方矩形表。
- `地图空间语义.txt`：给学员阅读的空间布局说明。
- `visual-contract.md`：32px 网格、角色脚底锚点、家具尺寸和回放验收标准。
- `assets/`：本案例地图素材目录。当前底图源文件为 `home-background.png`，另有同一书桌区域的整理前与整洁状态源图；背景和桌面切片已在浏览器导入，当前 Run 第 9 步已核对真实状态变化与桌面图片切换。

## 空间合同

World 是“陈明远的家·背景版”，Sector 是“住宅”。当前背景呈现卧室左上、书房右上、厨房左下、餐区右下和中间纵向通道。下方表格是浏览器已确认的 Arena、Game Object 边界；不要沿用旧 JSON 中的 24×24 房间坐标。

## 地图浏览器配置步骤

不要导入目录中的旧 `map-definition.json` 或 `collision-and-placements.json` 覆盖浏览器地图。按下面顺序在 Studio 中操作：

1. 新建 32×24、Tile 32 的地图，创建 1 个 World、1 个 Sector、5 个 Arena 和 4 个 Game Object，共 11 个节点。按下表填写稳定名称和边界（格式为 `x,y,width,height`）。
2. 导入 `assets/home-background.png`、`assets/desk-scattered-source.png`、`assets/desk-tidy-source.png` 三张 1448×1086 原图。World 绑定背景切片 `x=0,y=0,width=46,height=34`；两张桌面图都创建相同切片 `x=34,y=7,width=8,height=4`。
3. 在工作书桌 Game Object（`x=24,y=5,width=6,height=3`）上绑定整理前默认状态和顶层 `state=tidy` 整洁状态。其余节点不叠加图片素材。
4. 按碰撞矩形表绘制最少阻挡区域，保存后用四段路线检查验证可达性。出生点设为 `[9,5]`，书桌旁 `[23,7]`，厨房 `[10,15]`，餐区 `[22,17]`。
5. 头像和行走图在 Agent 页面上传后应用到本案例人群；本案例地图将“地图显示大小”设为 `3` 格，其他地图应按自身角色比例调整。再在实验中确认复制结果。当前进度便签版 Run 已完成 32 步晨间行为，完整背景、人物图、3 格显示和桌面状态切换已在实际画面确认；报告和导出状态见 `../settings/verification-record.md`。

### 路线检查

在地图编辑器中依次检查：`[9,5]→[23,7]`（16 格）、`[23,7]→[10,15]`（23 格）、`[10,15]→[22,17]`（14 格）、`[22,17]→[23,7]`（21 格）。这些是编辑器路径检查结果，运行回放仍需单独验证。

运行时应查询最终可走站位，再让 MOVE 使用同一个最终 `target_coord`，不要附带 `target_address`，也不要改用导航的 `next_coord`。当前 3 分钟步长与 4 格/分钟速度提供最多 12 格/步移动预算。工作书桌的 Game Object 范围被家具阻挡，应站在 `[23,7]` 操作，不把书桌对象地址当可走目标。

门洞、碰撞和操作站位已按实际背景在浏览器中校准。World 当前已绑定完整底图素材；书桌两态切片、编辑器状态切换、当前 Run 第 9 步的真实状态事实与画面切换，以及卧室→书房→厨房→餐区→书房的生活动线已确认。远端导航超视野的改进点、质量报告和导出状态见 `../settings/verification-record.md`。替换或绑定素材时仍必须保持 Tile 尺寸、锚点和碰撞事实。
