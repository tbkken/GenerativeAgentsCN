# 场景与素材拆分方案

日期：2026-09-06。第一轮设计提案；未生成或导入资产。

## 1. 先明确：我们要让读者看见什么

一名学生站在活动室书桌前，将散开的学习材料整理成整齐的一摞。先只整理“讲义与笔记本”，不增加文具分类、抽屉开关、物品搬运和走动。

这比“讲义、书本、文具分别整理”的三阶段流程更容易说明。人物只有一个，整理对象只有一个，场景只有一间房。

第一版的拟议画面只有两种桌面状态：材料散放、材料码齐。角色实际提交状态变化之后，回放才可以显示码齐的素材。人物说“整理好了”不是状态变化的证据。

## 2. 素材不等于 Game Object

三种粒度应分开考虑：

- 视觉素材：为方便绘图、组合和替换而拆分的图片。
- 语义对象：角色能够感知、交互或引用的有稳定身份的节点。
- 状态变化：通过合法世界动作提交、能从事实还原的内容。

不能因为画了三本书就自动建三个对象；也不能因为导入一张整图就认为里面的所有物品都已经可交互。

## 3. 建议素材清单

| 素材 | 是否单独图片 | 是否拟建为语义对象 | 用途 |
| --- | --- | --- | --- |
| 房间地板、墙边及少量装饰 | 一张固定底图 | 对应 World/Sector/Arena 语义，不按装饰逐项建物品 | 提供环境，不包含人物和待整理的纸张 |
| 空书桌 | 独立透明 PNG | 桌面学习区或书桌 Game Object | 与背景分开，便于配置占地和站位；不把纸张烘焙在图中 |
| 学习材料：散放 | 一张透明 PNG | 拟议中与码齐状态属于同一个稳定对象 | 初始画面 |
| 学习材料：码齐 | 一张透明 PNG | 与散放状态共用同一身份 | 状态变化后画面，不新建一个“整理后的材料”对象 |
| 许知行 | 单独角色素材，按系统支持的角色格式制作 | Agent | 不烘焙进房间背景；第一版不要求专门的手部动画 |

拟议文件名：`room-base.png`、`desk-empty.png`、`study-materials-scattered.png`、`study-materials-stacked.png`。最终格式与像素尺寸需与管理台素材导入合同核对。

先不制作逐页动画、拿起放下动画、光照变化、第二视角或大量状态组合。两个状态图足以讲清“对象状态与回放”。

## 4. 构图草案

采用正交俯视视角，保持与当前地图体系兼容；不是近景透视插画。

```text
┌───────────────────────────┐
│            墙边            │
│                           │
│       ┌───────────┐       │
│       │ 学习材料   │       │
│       │ 空书桌桌面 │       │
│       └───────────┘       │
│             ● 许知行         │
│         桌旁可走站位        │
│                           │
└───────────────────────────┘
```

底图建议先以 768×768 制作，配置尺度暂按 12×12 格构思，仅用于构图讨论，不作为已确认的运行坐标。桌面不铺满整个地图，必须保留桌旁可走空间。材料应足够大，缩小到管理台常见视窗后仍可辨认散放与码齐。

两种材料状态图要有相同画布尺寸、相同锚点和同一组纸张/笔记本。码齐后可以占用更小的可见面积，但图像原点不能跳变。背景透明，不带桌面、地板、文字水印或额外阴影背景。

碰撞处理：人物不可进入桌体；材料作为桌面视觉对象不应额外堵住桌旁站位。交互范围与角色视野要覆盖材料对象，但不能通过任意放大范围掩盖站位问题。

## 5. 四层语义方案与建模选择

```text
学习空间（World）
└── 活动区（Sector）
    └── 活动室（Arena）
        ├── 书桌 / 桌旁学习区（Game Object，待确定）
        └── 学习材料（Game Object，只有单独可交互时才建立）
```

不增加“书桌下面再挂书本”的第五层；如果分成两个对象，它们是 Arena 下的同级节点。

页面能力核对后，从以下两种方式选择一种：

- 最小对象方案：只有一个“书桌学习区”对象，它拥有材料整理状态；空桌与材料是这个对象的视觉组合。对象数量最少，适合入门。
- 分离对象方案：书桌与学习材料是同级对象，材料拥有自身整理状态。只有管理台能明确支持叠放渲染、可交互站位和稳定感知时采用。

不要在未核对页面合同前同时混用两种方案。素材先分开制作，可以服务于两种配置，避免返工。

## 6. 与先前 ACT 入门设计的区别

先前方案只使用 ACT，记录“正在整理”等普通活动，不改变真实对象状态。该方案仍然是最小的系统入门实验。

现在希望呈现桌面整理前后的画面，这新增了“对象状态改变及其渲染”能力，不能再声称只验证 ACT。建议教材仍以一个故事呈现，但分成两个可独立运行的小版本：

1. 1A：观察并整理。只验证感知、ACT 和活动回放，固定桌面图，不宣称物品真实改变。
2. 1B：让变化可见。复用相同素材与人物，显式加入 SET_OBJECT_STATE、状态事实和状态对应的外观。

1B 拟议短流程：观察材料现状 → ACT 整理 → 后续一轮提交状态改变 → 观察并检查。每名角色每步最多一个世界动作，不能要求一次提交 ACT 后又提交 SET_OBJECT_STATE。

这里“整理状态”是用户定义的案例字段，不是要求系统新增内置整理桌面逻辑。Brain 用自然语言驱动流程；世界改变通过系统通用动作完成。

## 7. 必须先核对的能力，不能靠素材假装已经实现

1. 管理台是否支持对象初始状态的明确编辑与保存？
2. 角色是否可以从感知或真实交互反馈中获得整理状态？如果仅能通过被动 Skill 获得，需重新评估入门复杂度。
3. 对象状态能否绑定不同图片，并在回放中切换？仅支持状态文本或图标不等于支持图片变体。
4. 若空桌和材料分离，是否可稳定控制两者绘制顺序、站位与碰撞，不产生额外语义层级？
5. 状态变化是否包含对象稳定身份、before/after 等可还原事实？回退时间线能否恢复散放状态？
6. ACT 和状态修改分两轮时，读者能否清楚分辨“活动记录”和“对象实际变化”？

当前粗查 `web/static/replay-player.js` 可见对象状态归约及状态驱动 glyph 更新，尚不足以证明通用状态图片替换已经打通。因此本稿只提出素材与体验目标，不承诺导入两张图就自动切换。

若不支持，登记为具体能力缺口，交给用户决定修复或暂以 1A 教学。禁止在回放前端按 Step 硬切图片，禁止解析模型自然语言猜测该显示哪张图。

## 8. 下一份素材交付

先制作一张构图参考图：房间、空桌、桌面材料占位与角色站位都清楚。构图参考图用于评审，不直接当成所有运行物品的合并图。

构图确定后，再分别输出固定房间底图、空桌透明图、材料两种状态透明图。最后编写精确像素/格坐标和导入清单，才进入管理台构建。
