# 近期线上故障修复的设计复核

本轮为审查，不修改线上系统、不启动 Run。审查范围为附件冲突、详情传输、模型配置保存、执行前保存及局部 PATCH 保存；不等同于完整资源交换重构的全面审计。

## 结论

文件包事实源、Studio/Protocol/Runtime/Replay 边界、实验资源物理独立、密钥不入包、封存只读等原则未因这些修复改变。但最后两项保存/启动优化有两处已复现的回归，需要修复后才能认为这些路径闭环。另有传输性能与已有多文件提交的可靠性边界，不能用“全量测试通过”替代说明。

## 必须修复的回归

### A. PATCH 遗漏 Crowd 关系（新引入）

- `console-api.js:3170` 仅提交 experiment、simulation、results、models、agents；`workspace.py:290` 对应白名单也缺少 crowds。
- 同一 `saveDraft` 同时被智能体编辑与删除使用。`console-api.js:3821` 在变更 agent_key 时修改 crowd.agent_keys；`:3858` 删除 Agent 时也修改人群成员。这些修改在 PATCH 中被丢弃。
- 本轮在独立临时实验中创建一个 Agent 和包含该 Agent 的 Crowd，再改 Agent key 和本地 Crowd 成员，以实际 PATCH 请求提交，得到 422：`resource dependencies missing for crowd/audit-crowd: [('agent', 'audit-agent')]`。
- 原 Agent 和 Crowd 均保持原样，证明校验和回滚保护仍有效；但合法的成员编辑被阻断，违反资源关系应完整、一致保存的要求。
- 修正方向：将 agents 与 crowds 作为同一次事务的关联内容提交、校验和保存；遍历全部 saveDraft 调用方，避免只按概览表单设计通用保存合同。
- 验收：含 Crowd 的 Agent 重命名、删除及失败回滚；验证不存在悬空成员，也不静默移除无关成员。

### B. 保存失败不一定阻止启动（新增条件保存放大原有状态问题）

- `console-api.js:1240` 为允许后续操作继续排队，将 state.draftMutation 设为捕获错误后的 Promise。
- `:3184` 模型复制先修改本地 definition，再保存，失败时只提示，未设置 dirty 或回退本地模型。
- `:3887` 新启动逻辑等待这个已吞掉错误的 Promise，再仅凭 state.dirty 判断是否保存。若 dirty=false，会继续 seal 和 runs。
- 本轮使用 Node VM 执行真实 enqueueDraftMutation / publishAndRun 函数，在模拟保存失败且 dirty=false 时，观察到请求顺序为 seal、runs，没有重试保存或阻断。该验证未调用线上服务，也未创建正式 Run。
- 影响：页面可能显示尚未保存的新模型，而启动的仍是包内旧模型；模型复制以外直接修改 definition 再保存的操作也应检查。
- 修正方向：分别管理队列是否空闲与最近修改是否成功持久化；失败修改必须保留未保存状态或明确回退，启动要验证成功保存，不能只等待队列完成。不能简单删除 catch 并让整个队列永久失效。
- 验收：保存失败后立即预检/启动必须阻断；修复并成功保存后才能启动；后续正常保存不能被先前失败永久阻断。

## 逐项方法与设计原则

1. **附件冲突**：同一包内路径已由 ResourceSet 带入，后续地图附件收集再次带入相同字节。构建器改为同路径同字节复用，异字节拒绝。仍复制入包，未按名称绑定，未放宽路径或冲突校验。符合物理闭包与确定性交换原则。
2. **详情压缩**：Web 适配层启用 gzip，改变 HTTP 传输编码，不改变包、哈希或 Runtime 输入。实测 31,596,297 字节压缩为 588,941 字节。方向符合边界要求，但没有消除重复 JSON 与全量轮询，不能宣称彻底解决内存/性能问题。
3. **模型保存**：删除隐藏旧表单重建模型与 secret_ref 注入的逻辑，保存实验已有模型副本；只通过显式模型中心复制更新。credential_env 保留，实际密钥仍在机器上。符合实验独立性与凭据原则。
4. **跳过冗余保存**：未修改草稿不重复上传，设计目标合理；dirty 状态覆盖不完整，造成回归 B。
5. **局部 PATCH**：Web 只接收表单段；Studio 加包锁读取同一实验、合并段、检查内容摘要并复用完整校验。实验包仍完整自包含，不新增数据库事实源，不是 v1 兼容层。摘要为并发令牌而非业务 Revision。允许段按整段替换，并非字段级 JSON Merge Patch。遗漏关联段导致回归 A。

## 需要准确表述的现有边界

- `experiments.py:100` 的响应同时在顶层和 current_draft/current_published 中包含完整 definition；前端还会周期性读取完整实验。gzip 减少带宽，但仍有完整解析、复制与内存开销。局部 PATCH 返回也仍带完整定义。
- `transaction.py:9` 先暂存、校验，再逐文件原子替换；捕获普通异常时回滚。它不是整个目录在崩溃/掉电下的一次性原子交换。进程在多个文件替换之间被强杀时，except 回滚无法执行，可能留下一致性校验失败的包。本轮未做强杀故障注入，不把此推断写成已发生的线上事故。
- 该多文件提交机制并非此次 PATCH 新增，但 PATCH 复用了它。此前“原子保存”的描述过强，准确说法应为“包锁串行、先完整校验、单文件原子替换、普通异常回滚”。
- 模型相关 422 有代码和回归证据，原用户日志仅记录状态码；不能声称抓到了每次原始 422 的完整错误体。502 在大请求保存路径复现，改成小请求后成功，但未取得代理内部超时诊断，不能断言具体由哪一跳代理触发。
